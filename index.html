2.9.0 Save Games: Added player-facing Save Game and Load Game files. A save downloads as a named JSON file with save metadata, app/state version, timestamp, room information, checksum, and the complete existing serialized game snapshot. Load Game accepts both new 2.9.0 save files and legacy exported state JSON. When a save is loaded while multiplayer is connected, the loaded snapshot becomes the local game state and is immediately broadcast as the room's new authoritative gameplay STATE, allowing the existing server persistence layer to store it.

2.8.7 Restart / Reconnect Fix: Remote clients now keep requesting the server-authoritative room snapshot until ROOM_STATE or ROOM_EMPTY is actually received. The retry loop is read-only: outbound gameplay STATE remains blocked until restore completes. This closes the server-restart path where Render logged a successful ROOM_STATE send while the browser remained stuck on “requesting state”.

2.8.6 Client Authoritative Restore Fix: The deployed browser client is now explicitly versioned and forced fresh on deploy. Remote clients use JOIN for the authoritative restore handshake, apply ROOM_STATE before enabling mutation sync, and show a visible RESTORED status after the saved snapshot is rendered. Root and public index files are kept identical to prevent Render from serving a stale multiplayer client.

2.8.4 Restore Authority Fix: Remote join is now server-authoritative. The client cannot send gameplay state or start its mutation watcher until the server explicitly returns the persisted ROOM_STATE (or ROOM_EMPTY for a brand-new room). Restore errors are surfaced in the multiplayer status instead of being silently ignored.

2.8.3 Persistence Diagnostics & Load Fix: Logs every persistent SAVE/LOAD and re-reads the mounted disk whenever a reconnecting client requests room state.

2.8.2 Persistent Reconnect Fix: Fixed the reconnect race that allowed a freshly loaded browser to overwrite a persisted room before restoration completed. Remote clients now enter a join gate: the server explicitly returns ROOM_STATE for an existing room or ROOM_EMPTY for a new room. The client cannot broadcast gameplay state until that handshake finishes.

2.8.1 Persistent Multiplayer: Server-side room snapshots can now be written to a Render persistent disk. Reconnecting to the same room restores the latest saved state even after a server restart or redeploy. Gameplay rules and the proven 2.8.0 WebSocket synchronization remain unchanged.

2.8.0 Remote Multiplayer: Added WebSocket remote-room transport while retaining the proven local BroadcastChannel mode. The same gameplay-state protocol, ownership guards, 100 ms mutation watcher, Force Sync, and Sync Audit are reused over the network. The included Node server hosts the game and relays room messages, retaining the latest room snapshot for newly joining players. This first remote build still sends the complete game snapshot to all room clients; server-side private-hand filtering is the next security/privacy milestone.

2.7.3 Multiplayer Gameplay Sync Audit: Added a peer-to-peer Sync Audit that compares the gameplay-critical state in both connected windows: Round/phase/active Hero, Hero positions/HP/Actions/conditions, hands/deck/discard state, map tiles, enemies/HP/conditions, and Encounter/Search deck counts. Added direct ownership guards to Hero movement and card-play entry points so the wrong client cannot mutate another player's Hero through alternate UI paths. Existing 100 ms state mutation replication remains the transport mechanism.

2.7.2 Local Multiplayer Sync Fix: Fixed movement/state replication by adding a connected-state watcher that detects actual game-state mutations every 100 ms and broadcasts them, instead of depending only on render calls. Hero movement also explicitly schedules a sync. Remote updates refresh the watcher baseline to prevent echo loops. Added Force Sync as a test/diagnostic control.

2.7.1 Local Multiplayer: Added same-browser shared rooms using BroadcastChannel. Open the HTML in two tabs/windows, enter the same room code, assign one window Aldric and the other Lyra, and connect. Game-state changes are broadcast automatically; joining peers request the current shared state. Connected windows enforce Hero ownership for normal Hero actions and card play. This is a local networking test layer only: both clients still receive the complete serialized state, including both hands, so private-information filtering remains reserved for the online/server build.

2.7.0 Multiplayer Foundation: Added a transport-safe shared-game snapshot layer without changing combat, cards, map geometry, or turn rules. The full game state can now be serialized to JSON, exported, copied, imported, and restored. This is the foundation for room/server synchronization in 2.7.x. Active Location-placement prompts are intentionally not resumed across imported snapshots yet; network command/prompt ownership comes next.
